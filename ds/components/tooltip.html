Tooltip

Read-only hint surfaces. Ink-on-paper pill that appears on hover or keyboard focus. Three usage patterns: data-attribute (zero JS), explicit element (multi-line info), and disabled-wrap (the canonical reason-for-disabled affordance).

Pattern A · data-attribute (most common)

Add data-tooltip="text" to any element. Optional data-tooltip-pos="top|bottom|left|right" (top is default). No JS. Triggers on :hover AND :focus-visible — keyboard parity is mandatory.

<button class="btn btn-primary" data-tooltip="Save your changes">Save</button>

<button class="btn btn-ghost"
        data-tooltip="Discard unsaved changes"
        data-tooltip-pos="bottom">Cancel</button>

<!-- Positions: top (default) · bottom · left · right -->

Pattern B · info-icon · multi-line content

For longer explanations beside form labels or in column headers. Wider, supports links inside. Use a real <div role="tooltip"> element controlled by JS so screen readers pick it up via aria-describedby.

<label>
  Auto-shutdown after idle
  <span class="info-icon" tabindex="0"
        data-tooltip="Stops the resource when CPU drops below 5%..."
        data-tooltip-pos="right"
        role="button">
    <svg .../>
  </span>
</label>

Pattern C · disabled-with-reason (the switch case)

The most common product UI miss: a disabled switch/button with no explanation. Wrap the disabled element in .tooltip-wrap so the tooltip fires on the wrap (since :disabled blocks events on the control itself).

<span class="tooltip-wrap"
      data-tooltip="Read-only access · contact your admin to enable"
      data-tooltip-pos="right">
  <label class="switch">
    <input type="checkbox" disabled checked>
    Auto-shutdown
  </label>
</span>

Hint on truncated content

When a name or path is truncated with text-overflow: ellipsis, attach a tooltip carrying the full value. Cursor changes to help so the user knows there's more.

arn:aws:ec2:us-east-1:621534234521:instance/i-09f8e7a2b3c4d5e6f /projects/payments-api/services/checkout-handler-v2

Positions

PositionUse when
top (default)Trigger sits near the bottom of the viewport, OR trigger is in a row above other content
bottomTrigger sits near the top of the viewport (header, top nav)
rightTrigger is in a left-aligned form label or sidebar
leftTrigger is in a right-aligned cell (action menu, kebab, etc.)

CSS-only positioning is sufficient for most cases. For viewport-edge cases (tooltip would overflow), use a popper library (Floating UI) to flip to the opposite side.

When NOT to use a tooltip

InsteadReason
Critical info → inline copy or alertTooltips disappear · users miss them · don't rely on hover for must-know info
Interactive content (button, link) → Dropdown / popoverTooltips have pointer-events: none · the user can't click anything inside
Long-form help → inline help text or doc linkTooltip max width 260-320px · longer content scrolls off-screen
Touch / mobile primary actions → button labelsNo hover on touch · tooltips become unreachable
Validation errors → inline error rowErrors must persist until resolved · tooltip vanishes on mouseout

Accessibility

  • Keyboard parity · tooltip fires on :focus-visible, not just :hover. The data-attribute pattern handles this automatically; for explicit-element pattern wire it in JS.
  • Trigger must be focusable · if you're attaching a tooltip to a <span> or icon, add tabindex="0" and role="button".
  • Connect via aria-describedby · for screen readers, point the trigger at the tooltip's ID. The tooltip itself gets role="tooltip".
  • Escape dismisses · for explicit-element pattern, Esc should hide the tooltip without losing focus on the trigger.
  • Never trap focus inside a tooltip · tooltips don't contain interactive content. If you find yourself wanting Tab to enter the tooltip, you actually want a Dropdown.
  • Reduced motion · the 110ms fade is suppressed under prefers-reduced-motion: reduce.

Don't do this

✓ Do
Tooltip on a disabled control explaining the constraint
User learns why · doesn't bang on the dead button.
✗ Don't
Disabled button with no explanation
Feels broken · users have no path to resolution.
✓ Do
Short tooltip · 1-2 sentences · plain language
Read at a glance. Tooltips are interrupts; respect the user's time.
✗ Don't
Paragraph-long tooltip with bullet points
Use inline help text or a docs link · tooltips aren't articles.
✓ Do
Inline error row under a failed form field
Error persists · user sees it while typing the fix.
✗ Don't
Tooltip on the field that shows the error on hover only
User moves their mouse to type, error vanishes, user re-submits same broken value.
