Loading states · decision tree

The same fetch can need a skeleton, a spinner, a progress bar, or nothing · depending on how long, how much, and how often. This page tells you which to use when.

The decision tree

Expected durationPatternWhy
< 200msNothingFaster than perception. Showing a loader makes it feel slower.
200ms – 1sInline spinner inside the triggerSpinner replaces text in the button · field shows pending dot
1s – 3sSkeleton at the destinationReserve layout so content doesn't jump in. Mimic the final shape.
3s – 10sSkeleton + Nimbus search poseAcknowledge the wait. Personality reduces frustration.
> 10s · determinateProgress bar with % and ETALong jobs need a sense of progress · cancel button
> 10s · indeterminateStatus text that updates · "Connecting…" → "Authenticating…" → "Loading data…"Each line changes the user's belief that something is happening

The result-state matrix

Once the fetch returns, four outcomes exist. The UI must distinguish them clearly · the worst sin is showing "no data" when the fetch errored.

OutcomeStateUI
Data returned · > 0 rowsLoadedRender content
Data returned · 0 rowsEmptyEmpty state with Nimbus + CTA · "Create your first…"
Data returned · 0 after filterFiltered-emptySmaller empty state · "No matches · clear filters"
Fetch failedErrorError state · explain what went wrong · Retry button

Skeleton vs spinner · the rule

Skeleton when you know the destination layout (table, card grid, detail page). Spinner when you don't (button submitting, dropdown filtering, undefined surface).

Optimistic UI · when to skip the loader

For actions where success is the overwhelmingly likely outcome (toggle a checkbox, rename in place, like/star), update the UI immediately and reconcile in the background. If the request fails, revert + toast.

ActionOptimistic OK?
Toggle switch · star · pinYes
Inline renameYes
Add tag to rowYes
Delete · destructiveNo · always confirm + wait for server ack
Money movement · plan changeNo · the user must see "Confirmed"
Form saveNo · give explicit "Saving…" then "Saved"

Slow-connection handling

After 8s without a response, the spinner / skeleton is no longer informative. Switch to a status line:

Still loading · this is taking longer than usual. Cancel

After 30s: replace the loader entirely with an error-with-retry. Don't leave the user staring at a spinner indefinitely.

User actionState

Don't do this

✓ Do
Skeleton table rows · then real data appears in place
Layout doesn't jump. User's eye doesn't need to re-acquire.
✗ Don't
Centred spinner on blank page · then table pops in
CLS · the cursor was hovering nothing, now it's hovering "Delete".
✓ Do
"No projects yet · Create one"
Empty state with the action surfaced.
✗ Don't
Show 0-row table with column headers and no message
Ambiguous · is it loading? broken? actually empty?
